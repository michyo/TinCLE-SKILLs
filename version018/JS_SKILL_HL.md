# SKILL_HL.md - TinCLE JS High Level Skills Sheet

* **Copyright & License:** Copyright (C) 2026 michyo (Michiyo Tagami). All rights reserved.

This document provides advanced architectural guidelines for complex game projects. The instructions here override or extend the base `SKILL.md`.

Create a self-contained single-file Canvas game in pure JavaScript without external libraries or assets.

## 1. Code & Environment Rules
- **Header Line (Absolute Requirement)**: Line 1 (the very first character of the file) MUST start with `// "Game Title" (width, height)`. Do NOT put any decorative comments, empty lines, or header banners above this line. (e.g. `// "My Game" (640, 480)`).
- **Canvas**: Assume `<canvas id="tinclecanvas">` exists. Obtain context via `document.getElementById('tinclecanvas').getContext('2d')`.
- **Output & Multi-File Script Architecture**:
  * For standard single-file projects, output the primary entry point as `game.js`.
  * **Automatic Script Injection (Multi-File Support)**: Both `jgrscnzl` and `rjasplns` automatically scan the project root directory for all other `.js` files and inject them as `<script type="text/javascript" src="filename.js"></script>` tags **above (before)** the primary target script (`game.js`).
  * Subdirectories for `.js` files are strictly prohibited; all split scripts MUST be placed directly in the project root.
  * When splitting complex projects across multiple files (e.g., `constants.js`, `player.js`, `levels.js`), define global classes, utilities, or data objects inside those auxiliary files so that `game.js` can cleanly consume them.
  * Never wrap generated code with HTML or Markdown formatting tags in source files.
- **[CRITICAL SKILL ROUTING: External Map Data]**: If the user provides a JSON map file generated by the `bandpisa` map editor (or requests to build a game using it), you MUST immediately load or refer to the external skill sheet **`SKILL_BA.md`**. It contains the strict JSON parsing schema, multi-layer rendering logic, and semantic annotation rules required to correctly integrate the map into the JavaScript Canvas environment.
- **Audio Options (Hybrid)**: You can implement audio using either of the following approaches (or combine both):
  1. **Procedural Web Audio API**: Generate real-time BGM and sound effects procedurally using Web Audio API oscillators (`OscillatorNode`, `GainNode`, etc.).
  2. **External Audio Assets**: Load and play pre-rendered audio files (`.ogg` / `.wav`) using standard HTML5 Audio or Web Audio API buffer decoding. All external audio files MUST be generated or formatted at a **44100 Hz** sample rate. You can generate BGM using `pisstrak` (`SKILL_PT.md`) and sound effects using `fartbox` (`SKILL_FB.md`).
- **Graphics**: Draw all visuals purely using 2D Canvas primitives. Combine multiple geometric shapes/paths to compose expressive characters, sprites, and objects.
- **Windows Packaging Prerequisite**: Building the standalone Windows desktop version via `rjasplns` strictly requires NW.js (https://nwjs.io/). The directory of `nw.exe` binary MUST be added to the system PATH.
- **UI & HUD Overlay Rules (Canvas Visibility Protection)**:
  * **Single Canvas Standard**: Render in-game HUDs, scores, and text directly onto `#tinclecanvas` (or via Three.js textures/sprites) whenever possible. Avoid dynamically creating redundant full-screen overlay `<canvas>` elements.
  * **No Full-Screen Opaque/Shaded Backdrops**: If creating HTML/DOM UI overlays (e.g. menus, dialogue boxes, HUDs), the root overlay container MUST be completely transparent (`background: transparent; pointer-events: none;`). NEVER apply full-screen dark gradients, solid backgrounds, or shaded overlays (e.g. `inset: 0` with dark backgrounds) that cover the entire viewport, as they will obstruct and black out the 3D/2D game canvas in web browser environments.
  * **Self-Contained UI Panels**: Confine background colors and panels strictly to the specific UI boxes, cards, or buttons themselves (e.g., small dialog cards or HUD panels), ensuring the underlying `#tinclecanvas` remains 100% visible across all game scenes (TITLE, PLAY, RESULT).

## 2. Game Scene Flow (Mandatory)
Structure your code with a clear state machine supporting at least 3 distinct scenes:
1. `TITLE`: Shows the game title, controls guide, and "Press Space / Click to Start".
2. `PLAY`: The core playable game loop.
3. `RESULT`: Shows Game Over or Stage Complete screen, final score/records, and "Press R / Space to Restart".

## 3. Rapid Development Workflow & Audio Creation

TinCLE JS adopts an instant, web-first development loop. During active game development, always iterate, test, and debug in the browser environment. Do NOT package into Windows executables during everyday iteration.

### Builder Execution Role

- If you have command-line execution capability (Agent Mode / Terminal), execute the relevant build commands directly and verify output.
- If you are a conversational chat AI, provide the commands clearly and instruct the user to execute them.

### A. Web Iteration Loop (`jgrscnzl` & `churro`)

1. **Generate Web Output**:
  ```bash
  jgrscnzl game.js
  ```
  * Generates `index.html` from `tinclejs.html`.
2. **Launch Local Server & Browser (`churro`)**:
  ```bash
  churro [port_number]
  ```
  * Default port is `8000`.
  * Automatically launches the default web browser with Cross-Origin Isolation headers (`COOP`/`COEP`).
  * Press any single terminal key to cleanly terminate the server.
  * Open Developer Tools (F12) to inspect JavaScript console logs, exceptions, and live performance.

### B. Audio Asset Generation Workflows (`pisstrak` & `fartbox`)

When utilizing external audio assets rather than real-time Web Audio API oscillators, generate them using these standalone CLI utilities:

* **Audio Sample Rate (Strict Requirement)**:
  ALL audio files (both BGM `.ogg` and Sound Effects `.wav`/`.ogg`) MUST be encoded at a **44100 Hz** sample rate to prevent pitch distortion and speed glitches.
* **BGM Synthesis (`pisstrak`)**:
  Renders MML score files into `.ogg` or `.wav` using SoundFont synthesis:
  ```bash
  pisstrak <input.mml> [output.wav|output.ogg] [tail_seconds] [soundfont.sf2]
  ```
  * *Example:* `pisstrak mybgm.mml mybgm.ogg 0 soundfont.sf2` (Passing `0` tail_seconds is ideal for seamless looping BGM).
  * **[AI Rule]**: If you need to compose a new MML score from scratch, you **MUST** read and follow `SKILL_PT.md`.
  * **Advanced MIDI & Chiptune Rendering:** For MML-to-MIDI (.mid) conversion (for external DAW editing) or MIDI-to-Chiptune WAV/OGG rendering workflows, refer to `SKILL_MID.md`.
* **Sound Effect Generation (`fartbox`)**:
  Renders procedural 1-shot sound effects instantly into 16-bit 44.1kHz `.wav` files via named presets:
  ```bash
  fartbox -t <preset_type> -o <output.wav>
  ```
  * *Example:* `fartbox -t explosion -o explosion.wav`
  * *Available Preset Types (`-t`):* `coin`, `laser`, `explosion`, `powerup`, `hit`, `jump`, `blip`, `random`.
  * **[AI Rule]**: For complex parameter authoring, fine-tuning, or mutations (`.fart`), you **MUST** consult `SKILL_FB.md`.

## 4. Production Release Pipelines (Distribution Rules)

When generating final release builds or instructions, the AI **MUST** follow this structured multi-step pipeline.

### Step 1: Prep Assets & Credit Attribution Mandate (`CREDITS.txt`)

* **Enforce `CREDITS.txt` Attribution**:
  `CREDITS.txt` is distributed alongside both the Windows Desktop and Web builds, and its contents are viewable via the dedicated credit button at the bottom of the game screen on Web.
  * **Agentic AIs**: Must inspect and update `CREDITS.txt` in the root directory, listing attributions for ALL third-party assets, fonts, audio, and libraries added to the project. If license origins are missing, explicitly ask the user before finalizing.
  * **Chat-based AIs**: Must strongly urge the user to add all third-party assets/libraries to `CREDITS.txt` and provide a ready-to-copy snippet when context is available.

### Step 2: Code Obfuscation & Minification (`jalma`)

Before packing the final web or desktop distributions, the original JavaScript source files MUST be minified and obfuscated to protect the developer's pure C99/JS logic and drastically reduce payload size (for URLs, embedded storage, etc.).

1. **Minify Source Code (`jalma`)**:
  Use `jalma` (JAvascript Local Minifier & Alterer) to completely strip formatting, remove dead code, and mangle variable names.
  ```bash
  jalma game.js gamemin.js
  ```
  *(If the project is split into multiple `.js` files, minify each one individually, preserving their execution order for the builders).*
  **[CRITICAL WARNING]**: NEVER overwrite the original `game.js` with `jalma`. The minification process is irreversible (a "death" of readable code). Always output to a new file (e.g., `gamemin.js`) or directly into a staging release folder.

* **Extreme Payload Reduction (The "URL" Strategy):** By stripping all formatting, dead code, and mangling top-level variable names down to single characters, `jalma` often halves the filesize of pure TinCLE JS Canvas logic. This extreme reduction is critical if the AI agent attempts advanced deployment strategies, such as embedding the entire game payload into base64 URL queries or QR codes.
* **Logic Concealment (The "Black Box"):** Protects the custom game algorithms and pure C99/JS procedural logic from casual browser inspection, satisfying the release requirements of developers who prefer their source code remain a black box.

### Step 3: Web Browser Build Path

1. **Compile Web Target (Using Minified Code)**:
  ```bash
  jgrscnzl gamemin.js
  ```
  * Generates `index.html`.
2. **Distribution Checklist (Web)**:
  Place the following items into the release folder (e.g., `_release_web`):
    * `index.html`
    * `gamemin.js` (The obfuscated source, NOT the original `game.js`)
    * `libs/` directory
    * All audio/image assets referenced by the game
    * `.htaccess` (Ensures Cross-Origin Isolation on Apache servers)
    * `CREDITS.txt`
    * `readme.txt`

### Step 4: Windows Desktop Standalone Build Path (`rjasplns`)

1. **Compile Executable (Using Minified Code)**:
  ```bash
  rjasplns gamemin.js [game.exe]
  ```
  * Generates standalone `game.exe` (defaults to `game.exe` if omitted).
  * Automatically scans the current directory and bundles all game assets whose file extensions match those listed line-by-line in `exsass.txt` directly into the executable package. Ensure all used asset extensions (e.g. `.png`, `.ogg`, `.wav`) are registered in `exsass.txt`.
  * Automatically collects all necessary NW.js binaries (`.dll`, `.bin`, `.dat`, `.pak` files) and the `locales/` directory into the working directory.
2. **Check Dependencies (`depurant`)**:
  Run the generated executable in an isolated environment to verify that all necessary NW.js runtime dependencies (DLLs, etc.) have been properly collected and are not secretly being loaded from the system `PATH`:
  ```bash
  depurant game.exe
  ```
  *(If it fails to launch, you are missing NW.js runtime files in your folder. `rjasplns` usually handles collection, but this test guarantees a safe, standalone release).*
3. **Generate Icon (`icondom`)**:
  If a multi-resolution `.ico` icon is not yet prepared, convert your source image:
  ```bash
  icondom icon.png icon.ico
  ```
4. **Embed Resources (`poopee`)**:
  Embed the application icon and Windows manifest directly into the generated binary:
  ```bash
  poopee game.exe icon.ico manifest.xml
  ```
  *(Pass `"none"` if skipping either icon or manifest).*
5. **Distribution Checklist (Windows)**:
  Place the following items into the release folder (e.g., `_release_win`):
    * `game.exe` (with embedded icon, manifest, and internal asset bundle)
    * All NW.js runtime dependencies (`.dll`, `.bin`, `.dat`, `.pak` files collected by `rjasplns`)
    * `locales/` directory
    * `CREDITS.txt`
    * `readme.txt`
  *(Do NOT ship raw audio or image asset files in this folder; they are already packed inside the executable).*

### Step 5: Mandatory `readme.txt` Specifications

AI must explicitly include these details in `readme.txt` or platform descriptions:

* **Controls Disclosure**:
  * **Windows Desktop**: Mention standard window / fullscreen controls (toggle fullscreen via `F11` or platform default shortcuts).
  * **Web Browser**: Mention that clicking the on-screen canvas button toggles Fullscreen mode.
* **Creator Copyright**:
  * Display the user's copyright notice (`Copyright (C) 2026 [Developer/Creator Name]`).

### Step 6: Final Archive Packaging (`wipee`)

Automate the final ZIP archive generation using `wipee` (Whole Integration Packager for Executable Environment):

1. **Standard Packaging (Web / itch.io / General Distribution)**:
  ```bash
  wipee game_web.zip _release_web
  wipee game_win.zip _release_win
  ```
  * Generates a clean, standard Deflate ZIP archive.
2. **Scanner Bypass Packaging (Desktop Distribution Only - Optional)**:
  When distributing Windows desktop packages where over-reactive antivirus heuristic scanners might interfere, use the `-m` flag to activate Malformed ZIP mode:
  ```bash
  wipee game_win_secured.zip _release_win -m
  ```
  * **[CRITICAL] Never use `-m` for Web / itch.io builds.** Web hosting platforms require standard ZIP headers for automatic extraction.

### Components Authorized for Redistribution

The following components are fully authorized for royalty-free distribution within end-user game release packages, subject strictly to the condition that **`CREDITS.txt` is visibly included**:
  * `.htaccess`
  * `libs/` directory (including Three.js runtime files)
  * All NW.js runtime files generated by `rjasplns` (`*.dll`, `*.pak`, `*.dat`, `*.bin`, and `locales/`)
  * `CREDITS.txt`
  * `readme.txt`

## 5. Custom GLSL Shader Development & Validation (`pisschk`)

When implementing advanced visual effects using custom GLSL shaders (such as Three.js `ShaderMaterial` or raw WebGL fragment shaders loaded from external `.frag` or `.glsl` files), all fragment shaders **MUST** be validated using `pisschk` to prevent cross-platform rendering failures (e.g. driver-specific bugs or reserved word crashes).

### A. Shader Writing Rules for TinCLE JS

1. **WebGL / GLES Compliance**: Write shaders compatible with WebGL 1.0 (GLES2) / WebGL 2.0 standards.
2. **Explicit Precision Header**: Unlike the C version of TinCLE, there is no automatic header injection. When writing raw standalone fragment shader files (`.frag` / `.glsl`), you **MUST** include precision specifiers explicitly at the top:
   ```glsl
   precision mediump float;
   ```
3. **Canvas Coordinates**: Canvas rendering resolution is strictly fixed to the declared game dimensions (`WIDTH`, `HEIGHT`). Therefore, standard normalized coordinates can be calculated directly via `gl_FragCoord.xy / u_resolution.xy` (or standard UV pass-throughs like `vUv`).

### B. Shader Validation Workflow (`pisschk`)

To guarantee that shaders run flawlessly across NVIDIA, strict AMD Radeon drivers, and diverse browser WebGL runtimes, validate every shader file before referencing it in `game.js`:
```bash
pisschk <shader_file_path>
```

* **Example**: `pisschk assets/shaders/water.frag`
* **Validation Coverage**:
  * **Strict Radeon Compliance**: Enforces rigorous GLSL syntax and blocks vendor-specific extensions and reserved identifier collisions (e.g., using `active` as a variable name).
  * **Web / GLES Compliance**: Verifies WebGL/GLES2 suitability.
* **Exit Codes**:
  * `0`: All inspection checks PASSED successfully.
  * `1`: Syntax/compilation errors DETECTED.
  * `2`: File I/O or argument error.

### [CRITICAL AI RULE FOR SHADER CODE]

Whenever the AI agent creates or modifies external GLSL shader files (`.frag` / `.glsl`), it **MUST** execute `pisschk` to verify that the shader passes all checks cleanly before finalizing the build.

### 8.1 tbrzilve (Flat-Root Multi-Stream ZIP Archiver)

`tbrzilve` (Tabrizi Lovuez: Tiny BRilliant ZIp LoVely Encloser) is a specialized, minimalist CLI archiving utility built on `miniz`. It flattens all input file paths down to their base names and packs them directly into the root directory of a standard ZIP archive (`MZ_DEFAULT_COMPRESSION`), intentionally tolerating duplicate filenames without collision checks or warnings.

#### CLI Syntax & Usage

```bash
tbrzilve <output.zip> <file1> [file2 ...]
```

* `<output.zip>`: Target archive path to create.
* `<file1> [file2 ...]`: List of files to pack into the archive root. Parent directories are automatically stripped (e.g., `a/data.bin` and `b/data.bin` are both written as `/data.bin`).

#### Core Architectural Characteristics & AI-First Advantages

1. **Deterministic Root Flattening (`get_basename`):**
  * Regardless of where source files reside on the host file system, `tbrzilve` extracts only their base file names and places them directly at the ZIP archive root (`/`). Subdirectory structures are completely discarded.
2. **Zero-Warning Duplicate Filename Tolerance (Multi-Stream Archive):**
  * Standard GUI extraction software enforces unique filenames, but the raw ZIP format specification inherently permits identical filenames across central directory entries. `tbrzilve` exploits this feature to pack identically named files (e.g., `stage1/data.bin` and `stage2/data.bin`) into the exact same archive root without renaming, overwriting, or throwing errors.
  * Files are stored sequentially in the exact order specified on the command line.

#### When the AI Agent MUST / SHOULD Use `tbrzilve`

* **Collision-Free Dynamic Packaging:** When bundling assets from different staging directories where identical filenames exist, and you want to bypass generating complex path-renaming scripts or token-heavy string manipulation logic.
* **Index-Based Asset Streaming:** When building custom asset packs where the TinCLE engine, custom C data loaders, or WebAssembly stream decoders inspect the archive by **entry index order (0-th entry, 1-st entry)** rather than unique string lookup keys.
* **Multi-Version Resource Snapshotting:** When bundling generational asset variations (e.g., `v1/config.bin`, `v2/config.bin`) within a single archive for sequential state playback or generational rollbacks.

### 8.2 oxtailst (Oxtail stew: Overwriter and eXchanger for Textfile's Assigned Inline Letters Substitution Tool)

`oxtailst` is a blazing-fast, Pure C99 command-line text substitution utility designed to safely and precisely overwrite assigned inline string patterns across source files, batch scripts, and markdown documentation without relying on heavy regular expression engines or multi-step token replacements.

#### CLI Syntax & Usage

```bash
oxtailst <input_file> "<search_string>" "<replace_string>"
```

* `<input_file>`: The target text file to be modified (e.g., `.c`, `.h`, `.md`, `.bat`, `.html`).
* `"<search_string>"`: The exact literal string to locate.
* `"<replace_string>"`: The exact literal string to overwrite with.

#### Core Architectural Characteristics & AI-First Advantages

1. **Automatic Backup & In-Place Execution:**
Before any modification occurs, `oxtailst` automatically generates a backup of the original file by appending `.bak` to the filename. It then processes the substitutions and overwrites the target file in place. If no matches are found, the file remains untouched and no backup is created.
2. **Safe Literal Substitution (No Regex Overhead):**
It performs strictly exact literal string matching. This prevents catastrophic cascading failures often caused by unescaped regular expression characters (like `.` or `*`) when manipulating dense codebase variables or sound parameter configs (like `p_freq_ramp = -0.150000`).
3. **UTF-8 Encoding Safety for Multi-Byte Characters:**
**[CRITICAL RULE]** When writing batch scripts (`.bat`) that utilize `oxtailst` to manipulate files containing multi-byte characters (such as Japanese text or emojis), you MUST ensure the Windows command prompt environment is set to UTF-8. You MUST insert `chcp 65001 > nul` at the beginning of the batch script prior to running `oxtailst` to completely prevent encoding corruption and mojibake.

#### When the AI Agent MUST / SHOULD Use `oxtailst`

* **Automated Version Bumping:** When building release pipelines (batch files) that must uniformly update version numbers across HTML templates, C/C++ headers, and markdown documentations simultaneously.
* **Targeted Parameter Swapping:** When generating automated scripts to swap specific hardcoded values (like API keys, endpoint URLs, or strict numerical constants) without risking the destruction of surrounding context.

### 8.3 ebisen (Easy Best-fit Image Size Equalizing Normalizer)

`ebisen` is a blazing-fast, pure C99 command-line image resizing utility designed to normalize scattered, raw visual assets into unified dimensions. Built without heavy external dependencies and utilizing high-fidelity resampling (Mitchell/Lanczos via the `stb_image` library), it ensures that game assets generated by AI or sourced from varied libraries maintain crisp, professional quality while fitting perfectly into the engine's strict dimension requirements.

#### CLI Syntax & Usage

```bash
ebisen <input_file> <target_w> <target_h> <mode> [output_file_optional]
```

* `<input_file>`: The source image file to resize.
* `<target_w>` & `<target_h>`: The desired output dimensions in pixels.
* `<mode>`: The resizing logic to apply (1 to 4).
* `[output_file_optional]`: (Optional) Explicit output file path. If omitted, defaults to `<input_file>_res.png`.

**Resizing Modes:**

* **Mode 1 (Fit):** Maintains aspect ratio, shrinking/expanding the image so it entirely *fits inside* the target dimensions. (Output size may be smaller than target).
* **Mode 2 (Crop):** Maintains aspect ratio, scaling the image to *completely fill* the target dimensions, automatically cropping any overlapping excess from the center. (Output size strictly matches target).
* **Mode 3 (Pad):** Maintains aspect ratio, fitting the image inside the target dimensions and padding the remaining empty space with solid black (Letterboxing). (Output size strictly matches target).
* **Mode 4 (Stretch):** Ignores aspect ratio, forcibly stretching the entire image to match the target dimensions. (Output size strictly matches target).

#### Core Architectural Characteristics & AI-First Advantages

1. **High-Fidelity Resampling in Pure C99:**
Bypassing bloated image processing runtimes, `ebisen` utilizes STB's high-quality Mitchell filter (equivalent to Lanczos) to prevent visual artifacting (like halos) when scaling down large AI-generated assets, ensuring pristine pixel delivery.
2. **Deterministic Layout Control:**
AI agents can select the exact normalization strategy required for the UI or sprite layer without relying on complex image-manipulation math or external GUI graphics tools.
3. **In-Place Output Optimization:**
By utilizing the optional 5th argument, AI agents can directly output the resized image to the final required filename (or overwrite the original) in a single command thrust. This eliminates the need for secondary file-renaming operations, optimizing context limits and token usage.

#### When the AI Agent MUST / SHOULD Use `ebisen`

* **Asset Normalization Pipelines:** When integrating multiple AI-generated graphics or disparate textures that must conform to a strict sprite grid or background resolution before being packed by `asspack`.
* **Batch Script Automation:** When generating `.bat` deployment scripts that need to instantly align entire directories of raw images into uniform dimensions directly from the command line.

### 8.4 jalebi (Jules Audio Lufs Equalizing & Balancing Improver)

`jalebi` is TinCLE's official command-line utility for automatically normalizing and trimming audio assets.

## Features

1. **Loudness Normalization:**
   Automatically equalizes overall loudness to approximately -15 LUFS, ensuring all BGM and sound effects are consistent and comfortable.

2. **Silence Removal (Trimming):**
   Automatically detects and removes absolute or near-silence at the start and end of the audio file, eliminating delay in sound effect playback and ensuring seamless loops.

3. **Standalone Single-Executable:**
   Built natively as a single pure C99 program without heavy external dependencies.

## Usage Instructions

```bash
jalebi <input.wav|input.ogg> <output.wav|output.ogg> [--keep-silence]
```

### Arguments:

- `input.wav` or `input.ogg`:
  The raw audio file to be processed. Currently, only standard `.wav` (PCM 16-bit) and `.ogg` formats are supported.

- `output.wav` or `output.ogg`:
  The destination file. The format is determined automatically by the extension provided. `jalebi` can easily convert formats (e.g. from `.wav` to `.ogg`) during processing.

- `--keep-silence`:
  An optional flag. By default, `jalebi` automatically trims silence from the beginning and end of the track. Include this flag if you want to bypass the trimming step and only apply the LUFS normalization.

### Example Workflows for AI Systems

**Normalizing a Sound Effect:**
When an AI generates an explosion sound effect, it can ensure the sound is punchy and without leading silence by running:
```bash
jalebi raw_explosion.wav ready_explosion.wav
```

**Normalizing Background Music without Trimming:**
If a track requires a specific silent padding to keep rhythm correctly, run:
```bash
jalebi bgm_raw.ogg bgm_final.ogg --keep-silence
```
